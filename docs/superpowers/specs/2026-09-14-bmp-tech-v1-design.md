# BMP Tech V1 — Canonical Design Spec

**Date:** 2026-09-14  
**Project:** BM-BMP  
**Surface:** `/bm-tech`  
**Status:** Design approved in conversation; awaiting user review of written spec before implementation planning  
**Implementation branch (to be created by Codex before any source changes):** `feat/bmp-tech-v1`

## 1. Purpose

BMP Tech V1 is the systems-and-tools surface of BM-BMP. Its job is to prove technical capability by showing how practical business systems behave, not by presenting a generic agency services page or a gallery of abstract “AI” claims.

The strategic separation between the three production surfaces is:

- **BM Visual:** perception, transformation, brand presentation.
- **BMP Creator:** imagination, authored worlds, discovery.
- **BMP Tech:** operation, systems, causality.

BMP Tech must remain visually and behaviorally distinct from both Visual and Creator while reaching the same execution bar: precise typography, controlled motion, strong art direction, responsive fidelity, and a polished interactive finish comparable in quality—not layout or visual language—to top-tier interactive studios such as Lusion.

The canonical product thesis is:

> **BMP TECH — SYSTEMS IN MOTION**

BMP Tech is not an “AI showcase.” AI may participate in systems, but the deliverable is a useful business tool, workflow, integration, operational interface, support/lead flow, lightweight CRM/dashboard, focused web system, MVP, or practical digital prototype built around a real operational problem.

## 2. Approved Product Direction

V1 uses the **Flagship System First** approach.

The page is organized around one concrete proof system: **AI Social Media Posting System**. That system demonstrates the Tech methodology in motion. It is not allowed to define the full scope of BMP Tech.

The flagship uses a **real-core + designed-future-layers** truth model:

- Existing or independently evidenced functionality may be marked **ACTIVE** or **VERIFIED**.
- Future functionality may appear only as **PLANNED**.
- No unsupported metric, uptime figure, post count, conversion result, production claim, integration state, or fake telemetry may appear.

The page later expands from this one proof into the broader BMP Tech capability spectrum.

## 3. Experience Model — Systems Observatory

The approved visual model is **Systems Observatory**, with approximately 20–30% influence from technical-blueprint language.

The visitor should feel that they are observing a system change state in real time. They should not feel that they are browsing a SaaS dashboard, developer portfolio, terminal simulation, or Creator-style cinematic world.

Core visual principle:

> **A system is understood through state, dependency, decision, and consequence.**

The site should communicate technical sophistication through causal clarity rather than visual noise.

## 4. Signature Entry — System Boot / Signal Acquire

BMP Tech has a short signature loading/entry sequence that represents system initialization.

### Behavior

First visit in a session:

1. Near-black / graphite field.
2. A single focal signal appears.
3. Two to four routes establish from that signal.
4. Geometry aligns and locks.
5. State language passes through a restrained sequence such as `SIGNAL → ROUTE → VERIFY → ONLINE`.
6. The final topology hands off into the opening observatory instead of disappearing as a disconnected splash screen.

Target duration: approximately **700–1200 ms**, never intentionally extended to simulate loading.

Returning visit within the same session: skip or reduce to a very short reacquire state (roughly 0–300 ms).

Reduced-motion: near-instant simple state reveal such as `BMP TECH / SYSTEMS ONLINE`.

### Rules

- Loader is an identity layer, not a performance mask.
- Loader must never own access to page content or become a hard blocker.
- No spinner, fake terminal, code rain, cyberpunk scanline, glowing AI orb, corporate logo intro, or generic progress bar.
- Boot and hero must use the same topology language so the entry feels continuous.

## 5. Homepage Architecture

The approved page sequence is:

1. **Boot / Signal Acquire**
2. **Opening — Systems in Motion**
3. **Flagship System — AI Social Media Posting System**
4. **Human Decision Checkpoint**
5. **System Evidence**
6. **One System → Many Business Systems transition**
7. **Business Tool Spectrum / System Families**
8. **Systems Register**
9. **Closing — Tell Us the Problem**

The page must not contain sections merely because a conventional website usually has them. Every major block must prove at least one of: capability, causality, operational usefulness, system maturity, or business applicability.

## 6. Opening Composition

Opening copy:

**BMP / TECH**  
**SYSTEMS IN MOTION.**

Supporting line:

> Tools and operational systems built around real business problems.

The hero should remain concise. It should not begin with a service list or generic agency description.

Suggested micro-state vocabulary:

`OBSERVE / ROUTE / DECIDE / OPERATE`

The system field behind the opening should already be alive but restrained. The first scroll should cause the field to resolve into the flagship system, not simply move the hero off screen.

## 7. Flagship System — AI Social Media Posting System

Introduction copy:

**SYSTEM 01**  
**AI SOCIAL MEDIA POSTING SYSTEM**

> A structured workflow for turning business inputs into reviewable publishing outputs.

Truth-state labels may include:

- `CORE SYSTEM / ACTIVE` when supported.
- `FUTURE LAYERS / PLANNED` for designed but unimplemented layers.

The flagship is represented as a single living system graph, not seven cards or a sequence of disconnected diagrams.

### Canonical state choreography

#### 01 — INGEST / BUSINESS INPUT
A structured business signal enters the system. Avoid a fake form or fabricated customer data.

#### 02 — STRUCTURE / NORMALIZE
Raw signal becomes usable structure: message, asset, channel, timing, constraints, or equivalent truthful primitives.

#### 03 — ROUTE / ORCHESTRATE
Dependencies and routing decisions become visible. The value is system logic, not third-party tool logos.

#### 04 — ASSIST / MACHINE CONTRIBUTION
AI may transform or propose a structured state. The site should use language such as **ASSISTED**, not **AUTONOMOUS**, unless autonomy is genuinely verified.

#### 05 — DECIDE / HUMAN CHECKPOINT
The system pauses at a clear human decision surface:

`APPROVE / ADJUST / HOLD`

This is a signature moment of BMP Tech.

Core statement:

> **AUTOMATION DOESN'T REMOVE THE DECISION.**  
> **IT MOVES THE DECISION TO THE RIGHT PLACE.**

The visitor should understand that BMP Tech designs human intervention deliberately rather than presenting automation as the removal of people.

#### 06 — EXECUTE / OUTPUT
The approved state propagates to its output destination(s). No unsupported output volume, engagement, or performance claims.

#### 07 — RETURN / FEEDBACK LOOP
Output may return into observation and adjustment. If automated feedback does not yet exist, it must be shown as **PLANNED**, not active telemetry.

### Choreography rule

Each state gets one dominant visual event:

- INGEST = enters
- NORMALIZE = disorder collapses into structure
- ORCHESTRATE = routes open/close
- ASSIST = data changes form
- CHECKPOINT = system pauses
- EXECUTE = decision propagates
- RETURN = signal loops back

Do not animate graph, text, counters, background, and decoration simultaneously without causal reason.

## 8. System Evidence

Heading:

**SYSTEM EVIDENCE**  
**WHAT EXISTS. WHAT OPERATES. WHAT COMES NEXT.**

This area behaves like an inspection ledger or technical manifest, not an analytics dashboard.

Example presentation grammar only:

- `CONTENT INPUT — ACTIVE`
- `ROUTING LOGIC — VERIFIED`
- `HUMAN REVIEW — ACTIVE`
- `AUTOMATED FEEDBACK — PLANNED`

Actual labels and states must be derived from audited implementation evidence before release.

No fake percentages, fake uptime, fake throughput, fake charts, or invented usage counts.

## 9. Transition — One System Is Not the Practice

Transition copy:

> **ONE SYSTEM IS NOT THE PRACTICE.**  
> **THE PRACTICE IS BUILDING THE RIGHT SYSTEM AROUND THE PROBLEM.**

The observatory zooms out conceptually so the visitor understands the social-posting workflow as one proof of a wider systems practice.

## 10. Business Tool Spectrum — System Families

Heading:

**SYSTEM FAMILIES**  
**TOOLS BUILT AROUND HOW BUSINESSES ACTUALLY WORK.**

The canonical business scope remains aligned with the existing BMP Tech service truth:

- Business websites & focused web systems
- Workflow automation and integrations
- AI-assisted internal tools and customer-facing utilities
- Chat / support / lead-handling systems
- CRM-lite and operational dashboards
- Custom MVPs and practical digital prototypes

These should be reframed as causal system families rather than service cards. Approved examples of presentation grammar:

- **WORKFLOW SYSTEMS** — `REPEAT → ROUTE → AUTOMATE → REVIEW`
- **INTERNAL TOOLS** — `INFORMATION → STRUCTURE → ACTION`
- **CUSTOMER SYSTEMS** — `QUERY → CLASSIFY → RESPOND / ESCALATE`
- **LEAD SYSTEMS** — `CAPTURE → QUALIFY → ROUTE → HUMAN`
- **OPERATION SYSTEMS** — `COLLECT → NORMALIZE → OBSERVE → DECIDE`
- **FOCUSED WEB SYSTEMS** — `NEED → INTERFACE → ACTION → RESULT`
- **CUSTOM MVPs** — `PROBLEM → PROTOTYPE → TEST → ITERATE`

This is a capability map, not a claim that every family has a live production product.

## 11. Systems Register

After the immersive system sequence, the page shifts to a precise technical register for clarity.

Heading:

**SYSTEMS REGISTER**  
**CAPABILITIES / APPLICATIONS / STATE**

Recommended columns:

- System type
- Business problem
- Delivery mode
- Capability state

For capability rows, terms such as **AVAILABLE** mean BMP Tech can deliver that class of system. They must not be confused with flagship maturity states such as **ACTIVE**, **VERIFIED**, or **PLANNED**.

## 12. Closing

Closing statement:

> **SHOW US THE PROCESS THAT SHOULD WORK BETTER.**

Supporting copy:

> We build practical tools and systems around the problem, the workflow, and the people who use them.

CTA:

**TELL US THE PROBLEM ↗**

The CTA preserves the existing canonical BMP Tech action language and keeps the commercial framing grounded in a real operational problem rather than generic “digital transformation.”

## 13. Visual System

### Typography

Use the shared BMP brand family, but apply it as instrumentation rather than expressive exhibition typography.

- Hero may be large but should not dominate the page like Creator.
- System labels, state names, identifiers, and metadata should be precise and crisp.
- Use tabular numerals where the existing type system supports them.
- Avoid overusing low-opacity type.

### Color

Base:

- Carbon
- Graphite
- Mineral white

Functional accents:

- **Signal:** restrained acid/electric green for active propagation.
- **Human Decision:** warm amber/orange.
- **Planned:** desaturated cool blue-grey.

Color indicates state, not decoration. No neon bloom or default “tech blue” aesthetic.

### Topology language

Supported primitives:

- Route
- Junction
- Checkpoint
- Payload
- Boundary
- Unresolved endpoint

Avoid generic network-circle diagrams. Human checkpoints should have a recognizably different geometry or state treatment.

### Grid

Grid is alignment infrastructure, not permanent decoration. It may appear selectively during calibration or comparison and disappear elsewhere.

### Depth

Use at most three conceptual layers:

1. foreground instrumentation
2. active system plane
3. background dependencies

No floating-card depth or Creator-style cinematic portal depth.

## 14. Motion Physics

Tech motion is **propagation**.

Canonical motion behavior:

`enter → route → pause → resolve → propagate`

Desired feel:

> mechanical initiation + elegant settling

Avoid bouncy springs, decorative parallax, perpetual float, or broad stagger animations.

Human checkpoint may deliberately slow the pacing.

### Scroll architecture

Native scroll remains authoritative.

Use:

`native scroll → raw semantic state → target visual state → tightly damped rendered state`

Raw state owns:

- active phase
- semantics
- accessibility
- section identity

Damped state owns:

- signal propagation
- transforms
- line reveal
- visual settling

Do not scroll-jack.

## 15. Technical Architecture

### Route

V1 stays on the existing production route:

`/bm-tech`

Do not rename the route during V1.

### Rendering strategy

Use **DOM + SVG first**.

DOM owns:

- text
- evidence
- labels
- register
- accessibility semantics

SVG owns:

- routes
- nodes
- signal paths
- boundaries
- checkpoint geometry

Three.js is already available in the repository but should not be used unless DOM/SVG cannot meet an explicitly demonstrated visual requirement.

Do not add GSAP, Lenis, D3, a graph library, or another animation dependency by default.

### Journey controller

Use one normalized controller/state source rather than independent section listeners.

Conceptual phases:

`BOOT → OBSERVE → INGEST → NORMALIZE → ORCHESTRATE → ASSIST → CHECKPOINT → EXECUTE → RETURN → EVIDENCE → SPECTRUM → REGISTER → CLOSE`

Controller output should include at minimum:

- global progress
- active phase
- phase progress
- direction
- velocity where useful
- reduced-motion state

### System data

Flagship topology must be data-driven. A system record should conceptually support:

- nodes
- routes
- boundaries
- maturity state
- dependencies
- human checkpoints

Truth state belongs in data, not hardcoded assumptions inside visual components.

Recommended maturity vocabulary:

- `active`
- `verified`
- `planned`

`VERIFIED` may be rendered only when actual evidence supports it.

### Evidence data

Evidence records are separate from visual topology but refer to the same system truth.

Conceptual fields:

- label
- state
- source/truth note

### Capability-family data

System Families use a separate schema because **capability availability** is not the same as **flagship implementation maturity**.

## 16. Responsive Design

Desktop: spatial systems observatory.

Tablet: simplified observatory with fewer simultaneous dependencies.

Mobile: a vertical causal system, not a scaled desktop graph.

Mobile causal sequence remains:

`INPUT → PROCESS → ASSIST → HUMAN CHECK → OUTPUT`

At 390px / DPR2:

- no horizontal overflow
- fewer simultaneous routes
- reduced sticky travel
- no pointer-only interaction
- crisp typography
- no continuous expensive effects

Signature is preserved even when spectacle is reduced.

## 17. Accessibility and Reduced Motion

The graph cannot be the sole carrier of information.

- Provide semantic DOM equivalents for causal stages.
- Decorative SVG routes should be hidden from assistive technology when duplicate text exists.
- Interactive checkpoint information must be keyboard accessible with visible focus.
- ACTIVE / PLANNED distinction must use structure/line style/labeling as well as color.

Reduced motion replaces propagation with resolved causal states. The page must remain fully understandable.

## 18. Performance Rules

Prefer:

- transforms
- opacity
- restrained SVG path animation

Be cautious with:

- large blur
- continuously animated filters
- large shadows
- full-screen masks
- large clip-path repainting

Do not render hundreds of decorative nodes. Complexity is justified only when it explains the system.

The loading signature must not delay usable content beyond its short identity window.

## 19. Cursor and Interaction

Desktop hover/focus may increase local contrast, reveal a state label, or inspect a dependency.

No large custom cursor.

Hover must never be required to understand or continue the main sequence.

The Human Checkpoint demonstrates `APPROVE / ADJUST / HOLD`, but the user is not required to make a decision to continue scrolling. Scroll remains the main narrative control.

## 20. Anti-Patterns

Reject:

- cyberpunk
- terminal walls
- fake code
- Matrix-style text
- glowing AI orbs
- glass dashboards
- floating SaaS cards
- integration-logo walls
- fake metrics
- blue-purple “AI” gradients
- Creator-style world portals
- repeated giant project typography
- BM Visual case-study grammar
- decorative animation without causal consequence

## 22. Release Quality Gates

BMP Tech V1 is not complete unless all are true:

1. With animation disabled, the surface still reads unmistakably as BMP Tech.
2. With explanatory paragraphs hidden, the flagship still communicates `input → processing → human decision → output`.
3. Screenshots do not resemble a generic SaaS landing page, Creator, or BM Visual.
4. ACTIVE and PLANNED are distinguishable through optics/behavior/labels, not only color.
5. Mobile preserves causality rather than merely preserving content.
6. Signature loading is short, distinctive, non-blocking, and continuous with the hero.
7. No unsupported proof or fake maturity state appears.
8. Final execution reaches the requested premium interactive-studio quality bar through BMP-specific system language rather than imitation.

## 23. Implementation Boundary

Before any source implementation begins, Codex must create a dedicated branch from the latest production `main`:

`feat/bmp-tech-v1`

Branch creation is a separate preparation step. No Tech V1 implementation should be made directly on `main` or on the preserved Creator branch.

The implementation plan should preserve Gateway, production root, BM Visual, and BMP Creator as locked surfaces except for the smallest shared-navigation changes strictly required by the approved Tech integration.
